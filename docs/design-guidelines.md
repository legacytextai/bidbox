# BidBox Design Guidelines

> **Status:** Authoritative Design Standard
>
> This document governs all BidBox interface decisions: information architecture, visual hierarchy, component behavior, interaction design, and UX principles. All future UI implementations are expected to follow it exactly. When conflicts arise between this document and individual implementation decisions, this document takes precedence.

---

## Design Philosophy

### Mission

BidBox exists to help contractors make better decisions under deadline pressure.

Every screen should answer a specific question as quickly and confidently as possible. The interface should reduce cognitive load rather than impress with visual effects. The goal is confidence, not excitement.

### Emotional Thesis

BidBox should feel:

- **Editorial** — structured, intentional, nothing extraneous
- **Authoritative** — contractors should immediately trust the software
- **Governmental** — the tone of official procurement, not a startup product
- **Calm** — clarity under pressure, never anxiety
- **Timeless** — not trend-driven; still appropriate in ten years
- **Precise** — every number, date, and status exactly where it is expected

The product sits at the intersection of:

- Bloomberg Terminal — information density with structure
- Apple Human Interface Guidelines — clarity of purpose
- Government procurement documents — authority and formality
- Financial dashboards — decision support under time constraints

BidBox should never feel playful, trendy, startup-ish, AI-generated, overly colorful, or crowded.

In implementation terms: sharp, no-frills, deadline-driven. Every UI decision should serve the user who cannot afford to make a mistake on bid day.

> A 55-year-old estimator should open any screen and immediately feel confident and supported.

## Core Design Principles

### Principle 1 — Clarity Above Everything

Every UI element exists to answer a question. If it does not answer a question, remove it.

### Principle 2 — One Screen, One Job

Every screen has one responsibility. Do not answer multiple unrelated questions on the same surface.

| Screen | Its one job |
|---|---|
| Opportunity Card | Should I click this project? |
| Opportunity Overview | Should we pursue this project? |
| Project Workspace | How do we win this project? |
| Intelligence Tab | Why did the AI reach these conclusions? |
| Proposal Tab | What needs to be submitted? |
| Estimate Tab | What are we pricing? |
| Subcontractor Tab | Who should cover this work? |

### Principle 3 — Progressive Disclosure

Information should appear only when it becomes relevant. Do not expose downstream workflow before the user reaches that stage.

```
Opportunity Discovery
↓
Opportunity Qualification
↓
Project Execution
↓
Continuous Monitoring
```

The UI mirrors this lifecycle. Earlier stages do not surface the controls or data of later stages.

### Principle 4 — Information Hierarchy

Users scan before they read. Every page has:

1. Primary information
2. Secondary information
3. Supporting detail

Never give all information equal visual weight.

### Principle 5 — Calm Under Pressure

Contractors experience enough urgency. The interface creates clarity, not anxiety.

Use color only when it communicates meaning. Never use color for decoration.

## AI Architecture → UI Architecture

Every AI capability has a permanent home. Nothing belongs in multiple places. No AI feature should be placed somewhere temporarily because it is convenient.

| Tab | Generated by | Purpose |
|---|---|---|
| **Overview** | Opportunity Intelligence Agent | Should we pursue this? |
| **Documents** | Document Acquisition Layer | Original source material |
| **Intelligence** | Knowledge Layer | Evidence, citations, reasoning |
| **Bid Readiness** | Qualification Agents | Can we submit? |
| **Proposal** | Proposal Agent | Submission package |
| **Estimate** | Estimating Agent | Pricing |
| **Subcontractors** | Coverage Agent | Coverage and outreach |

## Typography

### Type Scale

| Element | Size | Weight | Line Height | Usage |
|---|---|---|---|---|
| H1 | 28px | Bold | 1.5 | Project titles |
| H2 | 22px | Semibold | — | Section headers |
| H3 / Labels | 16px | Medium | — | Labels |
| Body | 14px | Regular | 1.6 | General text |
| Caption | 12px | Light | — | Metadata, timestamps |

**Font family:** `Inter, -apple-system, BlinkMacSystemFont, "Segoe UI", Roboto, Helvetica, Arial, sans-serif`

All spacing follows the 8pt grid baseline.

### Typography Hierarchy Principle

Large type establishes structure. Do not reduce font sizes to fit more content.

If content no longer fits at correct type sizes: reduce the content, not the readability.

> Tone: confident, no-nonsense, readable on jobsite iPads and office monitors alike.

## Color System

### Palette

| Purpose | Hex | RGB | Semantic meaning |
|---|---|---|---|
| **Primary (black)** | `#121212` | `18, 18, 18` | Text, backgrounds |
| **BidBox Blue** | `#1D4ED8` | `29, 78, 216` | **PRIMARY BRAND COLOR** — CTA buttons, links, accents, icons, navigation |
| **Accent Red-Orange** | `#D92D20` | `217, 45, 32` | Urgent states, failures, expiration — urgent badges only |
| **Soft Gray** | `#F4F4F5` | `244, 244, 245` | Backgrounds |
| **Outline** | `#E4E4E7` | `228, 228, 231` | Borders |
| **Success Green** | `#12B76A` | `18, 183, 106` | Success states, active license badges |
| **Job Walk Gray** | `#6B7280` | `107, 114, 128` | Job walk event badges (calendar) |

### Semantic Color Mapping

| Color | Meaning |
|---|---|
| Blue | Navigation, primary actions, links |
| Green | Success, confirmed, active |
| Red-Orange (`#D92D20`) | Urgency, failure, expiration |
| Gray | Neutral states, everything else |

Color communicates meaning, not decoration. Do not introduce new colors without a semantic purpose. Do not use the accent red-orange for non-urgent states.

### Contrast & Modes

- Minimum contrast: WCAG AA+ (4.5:1)
- Light and dark mode: use Tailwind `dark:` variant support
- Mood: urgent but not chaotic

## Motion & Interaction

- **File upload success:** 250ms fade-in with checkmark
- **Copy link:** 200ms glow on hover, ease-in-out
- **Countdown timer:** real-time smooth JS transitions (no jank); countdown digits remain **black**, not blue
- **Button hover:** soft background fill
- **Button tap:** compress 1px + subtle shadow
- **All motion durations:** 150–300ms

> Motion should confirm, never distract. Follow "Kindness in Design."

## Component Standards

### Opportunity Cards

**Purpose:** Answer *Should I click this project?* in under 5 seconds.

**Must display:**
- Project title
- Agency
- Bid due date
- Engineer estimate
- Portal
- County (if available)
- Intelligence status

**Must never display:**
- Executive summaries
- AI findings
- Long descriptions
- More than one badge per card
- More than one CTA button

Cards should feel quiet. Whitespace is more valuable than additional information.

---

### Opportunity Overview

**Purpose:** Answer *Should we pursue this project?*

**Required sections — always rendered, never removed:**

1. **Project Snapshot** — Agency, Department, Solicitation Number, Bid Due, Job Walk, Engineer Estimate, County, Location, Portal, Contract Duration, Liquidated Damages. Nothing else. Contract Duration and Liquidated Damages belong here because they are project-level facts used in go/no-go evaluation, not dates or bidding requirements.
2. **Executive Summary** — The complete intelligence briefing for go/no-go evaluation. One section, no sub-divisions. Content reads in order: AI-generated prose paragraphs (scope, what's being built, major risks) followed by a requirements list (license requirements from portal metadata, then critical bid requirements from intelligence: Bond, Insurance, DIR, Prequalification). The requirements list appears within the same section container, separated by a subtle rule — not in a separate card. Do not concatenate or mechanically append; the section should read as one coherent briefing prepared by a senior estimator.
3. **Bid Items** — Scope summary table. Every portal renders the same columns: Qty, Unit, Item Description. The extraction pipeline may vary; the presentation must not.

Do not create miscellaneous sections. "Quick Facts", "Key Dates", and "Key Requirements" are not canonical sections — they are anti-patterns. If content does not belong in one of these three sections, it does not belong on the Overview. Documents belong in the Documents tab, not the Overview. Additional dates from intelligence (beyond Bid Due and Job Walk) are surfaced in the Intelligence tab, not the Overview.

When data is unavailable, sections display N/A, Not identified, or Preparing. Sections are never removed because data is missing.

---

### Project Workspace

**Purpose:** Answer *How do we win this project?*

The workspace is operational. It contains: Bid Readiness, Proposal, Estimate, Coverage, Team Collaboration, Addenda, Calendar, Tasks.

Opportunity qualification does not belong in the Project Workspace. That work happens in the Opportunity Overview before Add to Calendar.

---

### Tables

Tables are preferred over cards whenever the user is comparing structured data.

**Use tables for:** Bid Items, Subcontractors, Document Inventories, Requirements.

**Table rules:**
- Align text left
- Avoid zebra striping
- Use subtle borders
- Prioritize readability over visual interest

---

### Badges

Badges indicate state. They are never decorative.

**Good badges:** Intelligence Ready, Needs Review, Preparing, Expired, New Addendum.

Badges should be rare. Do not create a badge because data has a status. Ask whether the status requires a visual signal or whether plain text serves better.

A badge should never communicate data that could simply be text.

---

## Empty States

Every section always renders, regardless of whether data is available.

| Data state | Display |
|---|---|
| Field is null | N/A |
| AI has not run | Not identified |
| AI is running | Preparing |
| Data requires manual review | Needs review |

The page structure remains stable. Layout never collapses because a section is empty.

---

## UX Anti-Patterns

Never do the following:

- Shrink typography to fit more content — reduce the content instead
- Create colorful pills because a data field has a status
- Move information into unrelated sections for convenience
- Place Engineer Estimate under Key Dates
- Redesign existing UI without explicit direction
- Increase information density without increasing clarity
- Add badges because they look nice
- Duplicate information across sections
- Hide critical information behind additional clicks
- Create inconsistent layouts between portals

When uncertain: choose the simpler solution.

---

## System Consistency

- Use `shadcn/ui` component patterns throughout
- Buttons share radius, padding, and font size
- File upload uses a consistent drag-drop zone across GC and public views
- Form styling uses shared components: `<Label>`, `<Input>`, `<TextArea>`
- Status badges: use "active" (green) consistently for both Private Pool and Network Pool
- Calendar events: header/badge first ("Bid Due" or "Job Walk"), project name second, datetime third

---

## Print Design Patterns

### Iframe-Based Printing

When CSS-only print solutions prove unreliable across browsers, use the iframe approach:

1. Generate self-contained HTML with inline styles
2. Create hidden iframe and inject content
3. Set document title for PDF filename (browsers use title for Save-as-PDF name)
4. Trigger `print()` from iframe context
5. Clean up iframe after printing

**Implementation reference:** `src/lib/calendarPrint.ts`

**Print styling requirements:**
- `@page { size: letter landscape; margin: 0.4in; }`
- `-webkit-print-color-adjust: exact` for color preservation
- Use explicit dimensions (no `auto` heights)
- Calculate row heights based on available space

## Accessibility

- All form fields must be labeled
- Buttons require `aria-pressed` and visible focus indicators
- Countdown timer: `aria-live="polite"` for screen readers
- File lists: screen-reader readable, `role="list"` with `listitem`

---

## Adaptive System Memory

- GC company name autofills on public confirmation
- Timezone-adjusted timestamps for bid submissions
- Store last used agency and location in localStorage for fast reuse

## Design Review Checklist

Ask these questions before every UI change:

**Purpose**
- [ ] Does this screen answer exactly one question?
- [ ] Does every UI element answer a question — or can it be removed?
- [ ] Is information disclosed progressively, not all at once?

**Readability**
- [ ] Can the user find the answer within five seconds?
- [ ] Did readability improve (or stay constant)?
- [ ] Did visual noise decrease?
- [ ] Did whitespace increase?
- [ ] Is typography at the correct scale — nothing shrunk to fit content?

**Information integrity**
- [ ] Is there any duplicated information?
- [ ] Is any critical information hidden behind extra clicks?
- [ ] Are empty states displaying N/A or equivalent — no missing sections?
- [ ] Are badge and color usage driven by semantic meaning, not decoration?

**Technical**
- [ ] Typography adheres to the 8pt grid
- [ ] Color contrast ≥ WCAG AA+ (4.5:1)
- [ ] All interactive states are visually distinct
- [ ] All motion durations are between 150–300ms

**Confidence test**
- [ ] Would an experienced estimator trust this interface?
- [ ] Does this layout evoke clarity under time pressure?
- [ ] Does motion confirm user action without distraction?

If any answer is No, the design is not finished.
